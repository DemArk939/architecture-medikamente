### Проведите аудит мер по обеспечению безопасности данных

Проблемные зоны:

- Отсутствие разграничения доступа к данным пациентов
  Любой сотрудник, прошедший доменную аутентификацию, имеет доступ к общему диску с данными клиентов.

- Файловый режим работы 1С
  Критичные базы бухгалтерского и складского учета работают в режиме файловой СУБД.

- Отсутствие аудита действий пользователей
  Системы не логируют, кто, когда и зачем открывал медицинскую карту или менял финансовый документ.

- Неструктурированное хранение чувствительных данных
  Файлы Excel и скан-копии хранятся хаотично, дублируются, нет версионности.

- Отсутствие шифрования данных
  Данные хранятся и передаются в открытом виде.

- Опасная обработка платежных данных.
  Взаимодействие с ККМ и Excel при двойном учете может нарушать требования безопасности платежных карт.

- Размытие ролей в IT.
  Администратор сети делает всё, технический директор совмещает роль архитектора и разработчика.
  Нет разделения на разработку и эксплуатацию (конфликт интересов).

- Уязвимость к атакам
  Открытый доступ по сети к общим папкам и файловым базам 1С делает их идеальной целью для вирусов, которые могут
  зашифровать всё разом.

## Задание 5. Разработка cutover-плана

### Обоснование выбора стратегии Parallel run

Для миграции медицинской информационной системы компании «Медикаменте» выбрана стратегия Parallel run.

Основные причины:

- Критичность бесперебойной работы – остановка записи пациентов или доступа к медкартам недопустима.
  Параллельная работа позволяет старой системе обслуживать клиентов, пока новая отлаживается.
- Постепенное наращивание нагрузки – можно переводить на новую систему сначала небольшую долю записей или отдельные
  функции, контролируя корректность.
- Возможность сравнения результатов – данные из старой и новой систем сверяются для выявления расхождений до полного
  переключения.
- Простой откат – при сбоях мгновенно возвращаемся на старую систему без потери сервиса.

Ограничения: требуется синхронизация данных, двойной ввод на начальном этапе, дополнительные ресурсы.

## Задание 6. Классификация данных

1. Принцип работы:

- Данные поступают в брокер сообщений (Kafka).
- Orchestrator читает сообщение, вызывает Schema Parser для определения полей.
- Поля последовательно передаются ML классификаторам и Confidential Data Classifier.
- Каждому полю и всей записи присваивается метка (PUBLIC, INTERNAL, CONFIDENTIAL, RESTRICTED) и категория (PERSONAL,
  MEDICAL, FINANCIAL и т.д.).
- Результат сохраняется в Metadata Store, а данные с метками отправляются в Raw-слой Data Lake.

4. Масштабируемость (scalability)

Горизонтальное масштабирование:

- Kafka: партиционирование топиков по ключу для параллельной обработки.
- Classification Engine: stateless микросервисы, развернутые в Kubernetes с HPA (Horizontal Pod Autoscaler) на основе
  нагрузки CPU/очередей.
- ML Classifier: сервер с поддержкой нескольких реплик и балансировкой.
